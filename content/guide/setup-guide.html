00Read this first

You are not learning to code this week, and you are not learning the terminal either. You are learning to run a small, modern web project on your own machine so that an AI agent can build inside it while you watch, judge, and direct. The setup below is the same setup a front-end engineer at any product company would have. That's the point: your portfolio won't be a template someone else designed. It'll be a real project that belongs to you. The starter Vinson made is a skeleton with placeholder words and a placeholder look; every visual decision on it is still yours to make.

There are three ideas that make everything else make sense:

  1. Apps you install once (VS Code, Node, Git) vs. packages that live inside each project (everything npm downloads). Section 01.
  2. Claude runs the commands; you read the results. The terminal is where that happens, and you'll learn to read it, not type into it. Section 03.
  3. The dev server (the thing showing your site) is what you leave running while you work. Save a file; the browser updates. Section 06.
Two ways to do every step

From Section 02 on, every step that involves a command is written twice. Say to Claude Code comes first. That's the one to use. Or type it yourself is folded underneath it; open it and you'll see exactly what Claude ran on your behalf.

Both stay true all week. Agentic tools are absorbing these commands fast, and you may never need to type one. But they're the plumbing under everything you'll ship, and a design engineer knows them. In week two, try typing a few. Nothing in this guide stops working if you do.

House rule

You give every instruction yourself. Vinson can sit next to you and tell you what to say, but his hands stay off your keyboard. And when Claude asks to run a command, you read it before you allow it. Watching someone else do this teaches you nothing; doing it once yourself teaches you everything.

01Two kinds of “download”

You'll download things two different ways this week, and confusing them is the number one source of “wait, where did that go?”

Apps from the web

  • VS Code, Node.js, Git, Chrome
  • Download from a website, run an installer
  • Install once for the whole Mac
  • Live in /Applications or system folders
  • You'll almost never touch these again

Packages from npm

  • Next.js, React, Tailwind, TanStack Query
  • Downloaded by a command Claude runs for you in the terminal
  • Installed per project, into the project folder
  • Live in a folder called node_modules
  • Listed in package.json so they can be re-downloaded anytime

Think of it like Figma vs. a Figma file's fonts and plugins. Figma is installed once. The specific fonts a file uses belong to that file. npm packages are the fonts and plugins; Node is Figma.

02Install the apps

Four installs and two accounts. Do them in this order; later ones assume earlier ones.

VS Code

The editor. Files on the left, code in the middle, terminal at the bottom, Claude on the right. Everything this week happens inside this one window.

  1. Go to code.visualstudio.com and click Download for macOS. It's one universal build for Apple Silicon and Intel.
  2. Open the downloaded .zip. It unpacks to Visual Studio Code.app.
  3. Drag that app into your Applications folder. (If you skip this, macOS keeps it in Downloads and it behaves weirdly later.)
  4. Open it. If macOS asks whether you're sure, say yes. Right-click its icon in the Dock → Options → Keep in Dock.

How you'll open a project, every day: drag its folder onto the VS Code icon in the Dock, or into an empty VS Code window. That's it. No Open dialog, no command. File → Open Recent works too once you've opened it once.

Or type it yourself

If you'd like to open folders from the terminal later, press ⌘⇧P, type shell command, and choose Shell Command: Install 'code' command in PATH. From then on, code . in a terminal opens the folder you're in. Optional this week.

Claude Code, the VS Code extension

This is the builder. It's a panel inside VS Code where you describe what you want, and it edits the files in your project and runs the commands the job needs. It's the same engine as the terminal version of Claude Code, with a graphical interface: you see diffs before they're applied, you can rewind, you can drag screenshots in.

  1. You need a paid Claude account (Pro or Max). Sign up at claude.ai first if you don't have one. The extension signs in with that account; no API key, no billing setup.
  2. In VS Code, press ⌘⇧X to open the Extensions view.
  3. Search for Claude Code. The publisher is Anthropic. Click Install.
  4. Look for the ✱ spark icon: in the top-right of the editor when a file is open, and in the left Activity Bar always. Click it.
  5. Click Sign in. Your browser opens; approve it; come back to VS Code. A Learn Claude Code checklist appears. Worth clicking through once.

The extension bundles its own copy of Claude Code. You do not need to install anything else for the panel to work. Typing claude in the terminal is a separate install (the terminal version) and is deliberately not part of this week. Section 08 explains when that becomes worth it.

Node.js

The engine that runs JavaScript outside a browser. Next.js needs it to run your site locally, and installing Node also installs npm, the tool that downloads packages. You never “open” Node. It just needs to exist.

  1. Go to nodejs.org.
  2. Download the LTS version (currently v24; “LTS” means long-term support, the stable one). Pick the macOS Installer (.pkg).
  3. Open the .pkg and click through: Continue, Agree, Install. It'll ask for your Mac password.
  4. When it says the install was successful, close it. Then quit VS Code fully (⌘Q) and reopen it, so it notices Node exists.

Video walkthrough if you want to see it done: How To Install Node.js on Mac. Any version of Node 20.9 or newer works for Next.js; LTS is the right pick.

Git

Version history for your project. Each time you save your progress you make a commit (a named save point), and sending those up to GitHub is what puts the new version online. On a Mac, Git comes with Apple's developer tools, and the easiest way to get them is to let something ask for them.

  1. Make a folder called Projects in your home folder: in Finder, Go → Home, then ⌘⇧N. This is where the site will live. Not Desktop, not Downloads, not iCloud Drive (iCloud syncing node_modules will make your Mac miserable).
  2. Drag that folder onto the VS Code icon in the Dock. VS Code opens on it. If it asks whether you trust the authors, say yes; it's your empty folder.
  3. Click the ✱ icon to open Claude Code, and ask:

Finds out whether Git is there, installs it if not, and puts your name on your save points.

Say to Claude Code
Is Git installed on this Mac? If not, install Apple's command line
developer tools. Then set my Git name to "Your Name" and my Git email
to you@example.com, the same email I'll use for GitHub.

If a macOS dialog pops up saying the command line developer tools need to be installed, click Install. It takes a few minutes. Claude will tell you when it's done and what it set.

Or type it yourself

Open the Terminal app (⌘Space, type terminal, return). Type git --version. If a version prints, Git is there. If a dialog offers the developer tools, click Install, wait, and run it again. Then tell Git who you are:

Tells Git your name and email, so your save points are stamped with them.

Terminal

% git config --global user.email "you@example.com"

Two accounts: GitHub and Vercel

GitHub is where the code lives online. Vercel is the host that turns that code into a public website, automatically, every time you push.

  1. github.com → sign up. Use a username you'd put on a résumé; it's public.
  2. vercel.com → Continue with GitHub. Don't make a separate password; linking the two is the whole point.

You won't use either of these until Section 05 and Section 09. Make them now so nothing blocks you later.

Or type it yourself

03The terminal: read it, don't type in it (yet)

A terminal is a text box that runs commands. Type a command, press return, the computer does the thing and prints what happened. This week, Claude does the typing. Two things still happen in there that you need to be able to see: the dev server runs in it, and errors show up in it. So you'll learn to read it. Typing into it is optional, and folded under each step for when you want it.

Open it inside VS Code

Press ⌃`. That's Control (the key labeled control, not Command) plus the backtick key, which is the one directly under esc on a Mac keyboard. Press it again to hide the terminal. ⌃⇧` opens a second one beside the first.

If the shortcut doesn't fire, use the menu: Terminal → New Terminal.

Why VS Code's terminal and not the Terminal app: it opens already inside the folder you have open, which is the same folder Claude is working in. What you see there is what Claude sees.

Read it

The line waiting at the bottom looks something like this:

Reading the prompt: who you are, which machine, and which folder you're in.

zsh
alex@Alexs-MacBook-Air portfolio % ▍

Your username, your computer's name, and then the folder you're currently in (portfolio), then a %. The folder name is the important part: it tells you where commands run. Above that line is everything that has happened so far. When something goes wrong, the answer is in the last two lines, usually in red. Read those; the wall of text above them is almost always noise.

Allow the command

When you ask Claude for something that needs a command (install the packages, start the dev server, save a checkpoint), it asks before running it, and the message shows the exact command it's about to type. This is the one habit that makes “ask instead of type” safe:

  • Read it. Even if you don't understand every word, you'll recognise the shape after a day: npm install, npm run dev, git push.
  • If it's the thing you asked for, click Allow.
  • If it isn't, or you don't recognise it, say no and ask what it's for. Claude will explain. Then decide.

Two rules, whoever is typing. Never run a command you don't understand, whether it came from Claude or a random website; ask what it does first. And if a command asks for your Mac password, that's sudo, and you almost certainly don't need it this week. Stop and ask.

04npm

npm is an app store for code, without the storefront. Instead of clicking Install, a command like npm install something downloads that package into your project. Every site like this one is built out of hundreds of these packages, the way a Figma file leans on fonts and plugins it didn't make itself.

The two files that matter

package.json is the shopping list. It names your project, lists the packages it depends on, and defines named scripts (shortcuts like dev and build). It's short, readable, and saved alongside everything else.

node_modules/ is the delivered boxes. It's where npm actually puts the downloaded code. It's enormous (tens of thousands of files), it's automatically excluded from Git, and you never edit anything in it. If it gets weird, ask Claude to delete it and install again; it comes back identical.

The four things you'll ask for

Say to ClaudeIt runsMeaning
“Install the packages”npm installDownload everything on the shopping list. After cloning a project, or when someone says “did you install?”
“Add TanStack Query to the project”npm install @tanstack/react-queryAdd one package to the list and download it.
“Start the dev server”npm run devRun the script named dev from package.json.
“Run a production build”npm run buildRun the script named build. Section 06.

You'll also see npx something go past: that runs a tool once without keeping it. (It's what made the template you're about to download.) And the line after npm install that says “added 340 packages” is normal. So is a wall of text. Read the last two lines; that's where problems show up.

05Get the project

You are not starting from a blank folder. Vinson built a starting copy: the site's skeleton, the design tokens (colours, type sizes, spacing), one sample case study, and this walkthrough. You make your own copy of it on GitHub, download that copy to your Mac, and have the packages installed. Three steps, then you never think about it again.

Decide where it lives

In the Projects folder you made in Section 02. Every project you ever make goes in there, one folder each. Not Desktop, not Downloads, not iCloud Drive.

Or type it yourself

Makes one folder to keep all your projects in, then moves into it.

zsh
% mkdir -p ~/Projects
% cd ~/Projects
# ~ means your home folder. mkdir makes a folder. cd moves into it.

Make your own copy on GitHub

  1. Open the template: github.com/CaptialK/portfolio-starter. Sign in to GitHub if it asks.
  2. Click the green Use this template button, then Create a new repository.
  3. Owner: you. Repository name: portfolio. Public or private, either works. Click Create repository.
  4. You now have github.com/your-username/portfolio. It has one commit, and it's entirely yours.

Why not just take a copy of Vinson's? A fork stays tied to his, and a plain copy leaves you nowhere of your own to send changes. Use this template gives you a fresh repository with a clean history that belongs to you, which is what Vercel needs in Section 09.

Download it to your Mac (this is called cloning)

Do this from inside VS Code, so VS Code handles the GitHub sign-in for you and you never have to deal with tokens.

  1. Open VS Code. Press ⌘⇧P, type git clone, choose Git: Clone.
  2. Choose Clone from GitHub. A browser window asks you to authorize VS Code. Approve it and come back.
  3. Type portfolio and pick your-username/portfolio from the list.
  4. When it asks where to put it, pick your Projects folder. Click Select as Repository Destination.
  5. VS Code asks Would you like to open the cloned repository? Click Open. If it asks whether you trust the authors, click Yes, I trust the authors. You are the author now.

Tomorrow, and every day after: the folder is at Projects/portfolio. Drag it onto the VS Code icon in the Dock, or into an empty VS Code window, and you're back in it. Then click ✱ to open Claude. That's the whole morning routine.

Or type it yourself

06Run it

A Next.js project has three modes, and each is one npm script. You'll live in the first one.

The dev server

Opens your site on your own computer and keeps watching it. Save a file; the browser updates in under a second. This is the loop the whole week runs on: Claude edits, you save, you look.

Starts your site at localhost:3000 and keeps it updating as you save.

Say to Claude Code
Start the dev server and keep it running. Give me the localhost link.
  1. Claude asks to run npm run dev. Allow it. It comes back with http://localhost:3000. Click it, or type it into Chrome. You'll see the portfolio homepage with a placeholder name on it. That placeholder is the first thing you'll replace.
  2. In VS Code, open content/site.ts. Change the tagline text, press ⌘S. Look at the browser. That's the loop.
  3. The server keeps running in the background for as long as VS Code is open. You don't have to look at it. To stop it, ask: “stop the dev server.” To start it again tomorrow, ask again.

localhost means “this computer.” 3000 is the port, a numbered door. Nobody else can see it; it's your private preview. Claude can also give you the Network address, which lets a phone on the same Wi-Fi see it. That's how you'll check it on your phone before it's online.

Or type it yourself
zsh · portfolio
% npm run dev

  ▲ Next.js 16.3.4 (Turbopack)
  - Local:        http://localhost:3000
  - Network:      http://192.168.1.24:3000

 ✓ Ready in 900ms

Started this way, the terminal now looks “stuck.” It isn't; the server is running and waiting. Leave it, and open a second terminal with ⌃⇧` for anything else. To stop it: click in that terminal and press ⌃C. To start again: ↑ then return.

The production build

Packs the whole site into the finished version, the exact thing a visitor gets. It also refuses to finish if anything is broken, which is what makes it your pre-flight check.

Packs the site into its finished form, and stops if anything is broken.

Say to Claude Code
Run a production build and tell me whether it passed. If it failed,
show me the first error and don't fix anything yet.

Do this before every push you'd show someone. If it fails, the site is broken and putting it online will fail too. Read the error, then say “fix that” and look at what changed. Green → safe to send up.

The table it prints is real information: every page of your site and how much code the browser has to download to show it. When a case-study page balloons because of a huge image, you'll see it here first. Ask Claude to read it to you the first time.

Or type it yourself

Run it in the second terminal, not the one the dev server is in.

Preview the build

“Serve the production build” (npm run start) shows you the finished version exactly as a visitor would get it, at the same localhost:3000. Nothing updates as you save, and none of the helpful error screens appear. Use it rarely, when something behaves differently online than it did on your machine. Then ask for the dev server back.

Where these come from

Open package.json. The scripts block is the menu. npm run <name> runs the line next to that name. That's the entire mechanism, and it's what Claude is reading when you say “start the dev server.”

The shortcuts npm run understands, as they appear in package.json.

package.json
"scripts": {
  "dev":   "next dev",
  "build": "next build",
  "start": "next start",
  "lint":  "eslint"
}

07What's in the folder

This is the part Squarespace hides from you. It's also the part that makes you employable: the ability to look at a modern project and know where things go. Here's what's in the template, and what each piece is for.

What every folder in the project is for.

portfolio/ ├── projects/ ← YOUR WORK. one folder per case study. add a folder, get a page │ ├── _template/ ← duplicate this to start one │ └── onboarding-redesign/ ← the sample. delete it when you have real ones ├── content/ ← your words. the folder you'll edit most after projects/ │ ├── site.ts ← your name, role, email, links │ ├── about.mdx ← the about page │ └── guide/ ← this walkthrough ├── app/ ← the pages. every folder here is a URL │ ├── layout.tsx ← the frame around every page: fonts, header, footer │ ├── page.tsx ← the homepage. what shows at / │ ├── globals.css ← design tokens (colors, type scale) + the Tailwind import │ ├── about/page.tsx ← /about │ ├── work/ ← /work, and one page per folder in projects/ │ └── guide/ ← this guide. delete the folder when you're done with it ├── components/ ← reusable pieces: header, footer, case-study sections, motion ├── lib/ ← code that reads projects/ and content/ and turns them into pages ├── public/ ← images and files served as-is. public/me.jpg → /me.jpg ├── docs/ ← Vinson's notes on how the template was built ├── node_modules/ ← downloaded packages. never edit, never commit ├── .next/ ← build output, appears after you run. ignore it ├── package.json ← the shopping list + scripts ├── package-lock.json ← exact versions of everything. don't touch, do commit ├── next.config.ts ← Next.js settings. mostly empty ├── tsconfig.json ← TypeScript settings. leave it ├── postcss.config.mjs ← wires Tailwind in. leave it ├── eslint.config.mjs ← code-quality rules. leave it ├── .gitignore ← tells Git to skip node_modules and .next ├── site.config.ts ← one switch: whether the guide shows on your live site ├── AGENTS.md ← rules for AI agents working in this project ├── CLAUDE.md ← what Claude Code reads first. your design system, in words └── README.md

How a URL becomes a file

Folders are addresses. This is the single most useful thing to understand, and there is nothing to set up anywhere. Make a folder inside app/ with a page.tsx in it, and that folder's name becomes the address. Case studies go one step further: a single page reads everything in projects/, so every folder you add there gets its own address without anybody touching the code.

How a folder's name turns into the address people visit.

app/page.tsx→yoursite.com/ app/about/page.tsx→yoursite.com/about app/work/page.tsx→yoursite.com/work projects/onboarding-redesign/→yoursite.com/work/onboarding-redesign

layout.tsx wraps every page beneath it. The root one in app/ is where your nav, footer, and fonts go once, so every page gets them. When you tell Claude “add a nav,” it goes there.

Components: Figma components, but real

A component is a reusable piece of UI: a project card, a button, the case-study hero. They live in the components/ folder; the header, footer, case-study sections, and the motion library are already there. A page is just a layout of components with content dropped in. If you've built a Figma library, you already think this way.

Styling: Tailwind

Tailwind is CSS as class names, written directly on the element: class="text-lg font-semibold text-neutral-900". It looks noisy at first. The reason it's the standard for agent-built sites is that every style is visible right where it's used, so Claude can read and change it without hunting through separate CSS files. Your design tokens (type scale, spacing, colors) get declared once in globals.css and referenced everywhere.

There's no “upload” step. Sending your work to GitHub is how it goes online: your files live in one place, and the hosting rebuilds the site from them on its own.

08Claude Code in VS Code

The panel is where you'll spend most of the week. Here's how to work it well.

Open it and set the mode

  1. Click the ✱ spark icon (top-right of the editor with a file open, or in the left Activity Bar). Or press ⌘Esc, which toggles focus between your code and Claude's prompt box.
  2. At the bottom of the prompt box is a permission mode indicator. On Pro and Max it starts in Auto, where Claude applies most edits without asking. Click it and switch to Manual for this week.

In Manual mode, every edit shows you a side-by-side diff and asks before applying, and every command shows you what it's about to run. That's slower and it's exactly what you want while learning: you see every change, you can reject it, and you start recognising what the code for “a card grid” looks like and what npm run build is for. Switch to Auto in a couple of weeks once the diffs stop being interesting.

Give it what to look at

  • @-mention files. Type @ and a file name (@page.tsx) and Claude reads it. Fuzzy matching works; partial names are fine.
  • Select code, press ⌥K. Inserts a reference to exactly those lines. “Make @page.tsx#12-30 a 3-column grid on desktop.”
  • Hold ⇧ and drag files into the prompt box to attach them. This is how you hand Claude a Figma export or a screenshot of what's wrong. Do this constantly. A screenshot beats three sentences.
  • Type / for the command menu: attach files, switch model, toggle extended thinking, manage plugins.

Undo with rewind

Hover over any message in the conversation and a rewind button appears. Rewind code to here puts every file back the way it was at that point. This is your safety net before you're fluent with Git. Try it once on purpose so you trust it.

The Session history button at the top of the panel lists past conversations; click one to resume it with full context.

Extension now, terminal version later

The terminal version of Claude Code is the same assistant with a text-only interface. It has a few things the panel doesn't: every slash command, tab completion, a ! shortcut for running shell commands, and easier setup for connecting external tools. Power users tend to end up there.

You are not a power user yet, and the extension is a better teacher: diffs you can see, rewind you can click, screenshots you can drag. Every command you read going past this week is the same command you'd type there; when the terminal version is worth it, it's one install and typing claude in the terminal you already know how to read. Both share the same conversation history, so nothing is lost by starting here. Give it two or three weeks in the panel first.

09First push, first deploy

The course covers the five things you'll say to Git daily, and the five commands underneath them. This section is only the first time, which has one extra step: connecting Vercel. Do it on Day 1, before anything looks good. A live URL that says “hello” is worth more than a perfect site that's still on your laptop.

Your first push

Because you made your copy from the template back in Section 05 and cloned it from VS Code, it already exists on GitHub, your copy is connected to it, and GitHub already trusts this Mac. Nothing to publish, nothing to sign in to. Send up the name change you made in Section 08:

Say to Claude Code

10When something breaks

It will. Almost all of it is one of these. Read the first line of any error; the rest is usually noise. Each fix is written as what to say; the command it runs is in brackets, for the day you'd rather type it.

You seeWhat it means · what to say
Chrome can't reach localhost:3000The dev server isn't running. “Start the dev server and keep it running.” (npm run dev)
Cannot find module …Packages are missing. “Install the packages.” (npm install)
Port 3000 is in useA dev server is already running somewhere. Next.js will just use 3001; either is fine. Or: “stop the other dev server.”
Red error overlay in the browserA code error in the file you just changed. Copy the first line, paste it to Claude with “fix this,” or click rewind.
Browser shows old contentFile isn't saved (look for a dot on the tab; ⌘S), or the dev server crashed. “Is the dev server still running? If not, start it.”
Terminal looks frozenThat's a dev server you started yourself, doing exactly what it should. Open a second terminal (⌃⇧`).
Vercel build failed“Run a production build and show me the first error.” Same error, easier to read. Then “fix that,” and push again. (npm run build)
Claude asks to run a command you don't recogniseSay no, and ask what it's for. Then decide. Nothing runs until you allow it.
zsh: command not found: nodeNode isn't installed, or VS Code was opened before you installed it. Quit VS Code fully (⌘Q) and reopen. Still failing → reinstall Node from nodejs.org.
npm ERR! … ENOENT … package.jsonWhoever ran it was in the wrong folder. Make sure VS Code has the portfolio folder open, not Projects or your home folder. (Typing: pwd, then cd into portfolio.)
EACCES: permission deniedSomething tried to install globally. You don't need to this week. Don't use sudo; ask what it was trying to do.

When stuck for more than ten minutes: screenshot the terminal, screenshot the browser, drop both into Claude with “what's wrong and what should we do?” Then text Vinson. In that order.

11Words you'll hear

terminal
The text box where commands run. Claude types into it for you; you read what comes back. The program inside it on a Mac is called zsh, the “shell.”
command
One line that runs. npm run dev is a command. Claude runs them; so can you.
allow
Claude's ask-before-running check. It shows the command; you read it and click Allow, or say no and ask.
PATH
The list of places your Mac looks for programs when you type their name. “command not found” means it's not on the PATH.
Node.js
Runs JavaScript on your Mac instead of in a browser. Next.js and npm both need it.
npm
Downloads packages into your project. Comes with Node.
npx
Runs a package once without installing it.
package
A chunk of someone else's code you download and use. Also called a dependency.
package.json
Your project's manifest: name, dependencies, scripts.
node_modules
Where downloaded packages live. Huge, ignored by Git, regenerable.
script
A named command in package.json. Run with npm run name, or by asking for it by name.
dev server
What shows your site at localhost:3000 and updates the browser every time you save.
localhost
This computer. localhost:3000 = this computer, door 3000.
build
Packing your files into the finished version that visitors actually get.
deploy
Putting a build on the internet. Vercel does it on every push.
repo
Short for repository. It just means your project folder, on your Mac or on GitHub.
commit
A named save point in Git. “Save a checkpoint.”
push
Sending your commits to GitHub.
framework
The structure your site is built inside. Next.js is the one here.
React
What lets a site be built out of components, the way a Figma file is. You won't write it; Claude will.
component
A reusable piece of UI. A card, a nav, a button.
route
A URL. In Next.js, a folder in app/ with a page.tsx.
Tailwind
Styling via class names on elements instead of separate CSS files.
TypeScript
A stricter way of writing the code that catches mistakes early. Invisible to you.
CLAUDE.md
A file Claude Code reads at the start of every session. Your project's rules go here.
CLI
A program you use by typing instead of clicking. Claude Code has one; you won't need it this week.
